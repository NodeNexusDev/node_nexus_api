# Решение проблем

Начинайте диагностику с HTTP-статуса, поля `detail` и request ID в
структурированных журналах. Никогда не добавляйте в вывод API-ключи, пароли и
приватные ключи.

| Симптом | Вероятная причина | Диагностика |
|---|---|---|
| `401 Unauthorized` | Ключ отсутствует, отключён, просрочен или неизвестен | Проверьте `X-API-Key` и состояние ключа |
| `403 Forbidden` | Ключ `read-only` попытался изменить данные | Выдавайте запись только при необходимости |
| `409 Conflict` | Имя ноды уже занято | Найдите ноду по имени |
| `422 Unprocessable Entity` | Ошибка схемы, cursor, параметра или ID | Прочитайте `detail` и сравните запрос со справочником |
| `429 Too Many Requests` | Процесс исчерпал окно rate limit | Сделайте паузу и проверьте настройки лимита |
| `503` при операции с нодой | Ошибка SSH или удалённого Docker daemon | Проверьте маршрут, порт, учётные данные, host key и daemon |
| `504 Gateway Timeout` | Операция превысила `REQUEST_TIMEOUT` | Найдите источник задержки до увеличения тайм-аута |

## Приложение не готово

`GET /ready` возвращает `503`, если проверка БД завершилась ошибкой:

```bash
docker compose ps
docker compose logs --tail=100 api
docker compose logs --tail=100 db
docker compose exec db pg_isready -U "${POSTGRES_USER:-postgres}"
```

Внутри API-контейнера `DATABASE_URL` должен использовать Compose hostname `db`.
Если `AUTO_MIGRATE=false`, примените миграции отдельно и проверьте текущую
ревизию командой `uv run alembic current`.

## Расписания и удалённый Docker

Расписания хранятся в памяти, исчезают после перезапуска и не координируются
между репликами. Используйте один процесс-владелец или внешний постоянный
планировщик. При ошибке Docker проверьте ноду и выполните на удалённом хосте
`docker version`, `docker info` и `docker ps`. Массовые операции могут
завершиться частично, поэтому проверяйте каждый результат.
